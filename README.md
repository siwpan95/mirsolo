把《热血传奇》（Legend of Mir 2, 1999）那套 MMORPG 内容，做成**一个人也能通关的单机 ARPG**：
三职业 / 比奇省打磨 / 地牢打宝 / 沃玛祖玛赤月 / 沙巴克攻城——但对手全是 AI。

- **技术底座**：`3dworld`（渲染与确定性工具链）+ `allin-engine`（ECS / 事件总线 / 固定步长）
  + `dse-core`（字典场景）+ `bloodmusic`（程序化音频）
- **零外部素材**：所有贴图 / 音效 / 模型都由代码生成
- **确定性**：纯整数随机流，同种子同结局；掉落与击杀序号绑定，读档重打不刷装
- **零 GL 可测**：逻辑层无窗口单测，headless 冒烟 3 秒跑完 2000 秒游戏时间

## 下载与运行（Windows 发行版）

无需安装 Python：到 [Releases](https://gitee.com/siwpan/mirsolo/releases) 下载
`mirsolo-v0.1.0-win64.zip`，解压后双击 `mirsolo.exe` 即开玩。

- 校验：压缩包内附 `SHA256SUMS.txt`，`certutil -hashfile mirsolo.exe SHA256` 比对。
- 存档：默认写在 exe 同级的 `saves/` 目录；数据表（`data/*.json`）已打包进 exe，
  也可用环境变量 `MIRSOLO_DATA` 指到自定义数据目录（改数值玩法用）。
- 命令行验收（可选）：`mirsolo-smoke.exe --ticks 20000 --json` 跑 headless 冒烟。
- 系统要求：Windows 10/11 x64，OpenGL 3.3+（集成显卡即可），无需其他运行库。
- 构建方法见 [scripts/build_exe.py](scripts/build_exe.py)（`pip install pyinstaller`
  后跑 `python scripts/build_exe.py`）。

## 设计要点

**1. 公式与施加分离。** `combat/formulas.py` 是纯函数（不建世界、不写文件），
`combat/resolver.py` 是唯一改血的地方。单测因此可以只测公式，
端到端测试只测"血掉没掉"，两边不互相将就。

**2. 每次 roll 都记账。** 结算结果带 `rolls`，"这刀为什么只打 3 点"
能还原到具体随机数：命中 roll / 攻 roll / 防 roll 逐项可见。

**3. 位置无关的随机。** 随机流名包含 `(seed, 实体 id 对, tick)`，
所以结算顺序不影响结果——回放可对任意单帧复算，不依赖"从头重跑"。

**4. 数据驱动，代码只认 ID。** 全部数值在 `data/*.json`；
引用的物品/怪物/职业/传送目标由 `GameData.cross_check()` 校验，
`scripts/verify.py` 把它做成门禁。

**5. MMO → 单机的转化。** 沙巴克攻城改为"佣兵小队 vs 守军 AI 分层布防"：
三道据点（外城门→内城门→旗台）依次推进，只有当前波次目标可被打
（其余目标 `invulnerable`，打了不结算而不是"砍得动"），守军按波次铺兵 +
定时增援（`max` 封顶），玩家倒下或超时判负。目标 `kind="guard"`
不走死亡奖励，奖励由战役结算统一发。顶部战役状态条常驻显示
波次/目标耐久/守军数/剩余时间。摆摊经济改为商店 + 市场模拟，
抢 BOSS 改为确定性种子世界（掉落熵进存档）。完整转化表见计划书。

**6. 幸运 9 = 把 roll 区间的下限抬到上限。** 传奇的"幸运 9 刀刀上限"在实现上
不是"概率打出上限"，而是 `hi − (hi−lo)×(9−luck)//9` 收窄 roll 区间：luck 0 与裸装
逐位一致，luck 9 塌成单点。这样每刀消耗的随机数个数在 0..8 之间完全一致
（随机流不会因为换装备而错位），代价是两个端点之外的取值仍是线性近似，
标记为 `CALIBRATE`（详见 `docs/数据口径.md` 的《幸运 9》一节）。

**7. 拍卖行是"寄卖行 + 确定性撮合"，四条约束缺一不可。** 单机没有别的玩家，
所以"卖给谁"由系统掷点决定：玩家定价（三档），系统在 `[floor, cap)` 内按
**线性衰减**的概率成交（`cap` = 商店买入价 × 1200‰，挂底价 = 满概率，顶到上限恒为 0）。
四条约束是：要价有上限、越贵越难成交、成交扣 10% 手续费、**挂单即离手**（物品进托管，
不能"挂着还能穿"）。概率曲线刻意选线性——它能被单测逐点钉住，而"更自然的曲线"
只能靠肉眼调。撮合的随机流名是 `auction:{seq}@{round}`，只含挂单序号与第几轮，
所以多挂/少挂一张单不会挪动别的单（详见 `docs/数据口径.md` 的《拍卖行》一节）。

**8. 佣兵复用怪物的一切，图鉴复用死亡事件的一切。** 佣兵的身体（`Attributes`/
`AiState`/`Vitals`）与怪物同构，走 `_build_combatant` 同一条构造路径，只靠
`kind="summon"` + `faction=0` 就让索敌/追击/出手/死亡清理全部生效——不另写一套 AI。
它的三条约束是：花金币、**等级门槛**、**到点必走**（`MercenarySystem` 到期解散，
不留尸体）。图鉴不另起一套记账，而是订阅 `EVT_DEATH` 并复用与死亡奖励**同一个**
`resolve_owner`，所以佣兵打死的怪既进掉落也进图鉴。首次解锁给一笔经验
（怪物经验的 50%，只给一次）——不给属性点，属性点会让战力脱离职业成长表
（详见 `docs/数据口径.md` 的《佣兵与图鉴》一节）。

**9. 特戒的数据形状：效果挂在物品上，接线只有一个入口。** 六枚戒指各自
在 `data/items.json` 里声明 `ring_effect` + `ring_param`（效果名与参数键由 loader
登记，`validate()` 强制齐全），代码里不写"如果是麻痹戒指就……"这种分支表。
六条效果按**触发时机**分三类：挨打类（护身/复活）挂在
`CombatResolver._damage`——那是全项目唯一允许改血的地方，而且顺序被钉死为
「魔法盾 → 护身 → 复活判定 → `take()`」；出手类（麻痹/火焰/破隐）挂在 `_apply`
之后；主动类（传送）走 `T` 键。三者的随机流都带 `ring:` 前缀，戴上或摘下戒指
不会挪动主伤害流的位置（详见 `docs/数据口径.md` 的《特戒六枚》一节）。

**10. 磨损按 item_id 记账，让"换一把洗耐久"走不通。** 没有实物实例 id
（背包是堆叠的），所以磨损记在 `Wear.points[item_id]` 上——语义是"这一类装备里
最破的那件"：打废了换一把同款，磨损照旧继承，想洗掉只有**花钱**两条路
（修理 / 卖掉再买一件新的，两者都在入手或修好时重置账目）。
磨穿不给属性但**仍占负重**（不然"打废装备"反而成了免费减重）；
全废修理费 = 买入价 × 300‰ × 磨损比例，由门禁 `wear-and-repair` 钉住
"修理必须比买新的便宜"。磨损的随机流 `wear:strike:` / `wear:hit:` 独立于主伤害流，
有测试断言"关掉磨损后同一场架的伤害序列一字不差"
（详见 `docs/数据口径.md` 的《装备持久度与修理》一节）。

**11. 死亡惩罚是延迟结算的：先倒地，再让玩家自己选怎么起来。** 致死那一下
**不扣任何东西**，只把人放倒（`Downed` 组件）；接下来 `DOWN_TICKS = 30` 刻（3 秒）
内可以按 `R` 花金币**原地复活**（只掉磨损），否则到期自动**回城**并走全额四件
（掉经验 / 掉金币 / 全身磨损 / 掉一件背包物品）。为什么非得延迟：原地付费复活
卖的就是"少掉点东西"，若死亡瞬间先扣光、原地再退回来，就得写一套退款逻辑——退多少、
掉出去的物品怎么吐回来、吐回来的还算不算"掉过"，全是说不清的账。推迟到选择的那一刻
结算，两档各算各的，**没有退款这条路径**。另外自动回城兜底是必须的：headless
没有交互，倒地后必须有确定行为；玩家死了不操作也不会卡住。
掉经验**绝不掉级**（夹到本级已积累为止），累计流水落在独立组件 `DeathLedger` 上
**只增不减**——这是"死了读档撤销惩罚"的防线（详见 `docs/数据口径.md`
的《死亡惩罚》一节）。

**12. 续航必须有两条腿：商店捆买 + 怪物掉落，缺一条就会卡死。** 只靠买，
穷的时候打不了；只靠掉，脸黑的时候干瞪眼。九档药水（红/蓝各小·中·大 + 超级红蓝 +
太阳水）的公共冷却是 **10 刻**，记在独立的 `PotionState.ready_at` 上而**不用**现成的
`Cooldowns`——那边是浮点秒、每帧递减（技能要的正是那种手感），而药水冷却必须落在
**整数刻**上，否则"同一 tick 的存档"会回放出一个"还差 0.03 秒"的冷却，回不了档也
对不上账。手动（`Q` / `E`）与自动（HP < 500‰ / MP < 300‰）共用**一本**冷却账，
分开放迟早长出第二套"自动刚喝完、手动这口算不算冷却中"的判断。
`PotionSystem` 的 priority 是 8，远在选敌（11）与出刀（28/30）**之前**——药效必须在
怪物这一 tick 挥刀之前进账，否则"血见底赶紧喝一口"会在同一 tick 里先挨一刀，
等于喝了个寂寞。自动喝药**刻意静默**（它每 tick 都可能发生，往屏幕上刷一行提示就是
噪音，血条动了就是反馈），手动那一路必须给回音——没药时按 `Q` 一声不吭，
和按键失灵没区别。挑药选"够用的里面最小的"（不浪费大药），回血走 `Vitals.heal`
（与 `RegenSystem` 同源；那条"唯一改血入口"的纪律管的是**伤害**，回血另有两处
既有实现）。商店按 `BUY_BUNDLE = 10` 瓶捆卖，并**按负重余量夹瓶数**——负重是物理
上限，法师 30 级裸装只有 49，红蓝各 10 瓶要 50，整笔拒绝会让人一次也补不了货；
**钱不够才整笔拒绝**，这一条从第一天起就没破过例。掉落表里药水那一组
**必须追加在 `groups` 末尾**：随机流名带组下标，插到前面会把既有装备组的掉落结果
全部洗牌（详见 `docs/数据口径.md` 的《药水与续航》一节）。

**13. 挖矿的代价是"武器槽被占"，不是一条补丁规则。** 鹤嘴锄就是一把武器
（攻击 1-3、占 `weapon` 槽、有耐久），所以"挖矿时攻击力减半"这种补丁不需要写——
这一刻你拿的是锄头，本来就打不动怪。矿石是**只进不出**的资源：不可装备
（无槽位）、不可寄卖（拍卖行的可交易集合里没有它）、耐久为 0（不是装备，磨不了），
但**有重量也有价**——重量让它挤占背包（挖到背不动为止），价格让它能在商店整笔卖掉。
矿石**不上架**：货架能卖矿石就等于能用金币直接买到纯度 100 的黑铁矿石，
#25 的升级成本当天崩盘。纯度是韩版传奇的特色，而纯度必须**长在 item_id 上**
（`ore_blackiron_1..4`，纯度 30 / 50 / 70 / 100）——背包是堆叠的、没有实物实例 id，
"这一堆黑铁是 70 纯度"这件事只能靠 id 区分（与 `wear` 按 item_id 记账同一条纪律）。

**14. 挖矿的两条随机纪律：矿点下标进流名，累计锄数绝不随再生清零。** 流名
`mine:{map_id}:{vein_index}@{swing_index}`，与战斗 / 掉落 / 磨损**全部**分开，
所以站着挖矿不会挪动任何一场架的读数（有测试逐位钉住）。`swing_index` 用的是
**累计**锄数 `total` 而不是"本轮第几锄"：矿脉枯竭后按 `regrow_ticks` 再生，
届时储量回到满、但 `total` 继续往上走——若随再生清零，流名就会重用，
长回来后前几锄必然挖出和上一轮一模一样的矿。同理，每锄**必磨 1 点**、
不掷点：生产成本不是战斗损耗，"锄头还能用多久"必须是可预期的，
而且不掷点就不消耗随机流，从原理上堵死了挪动战斗磨损读数的可能。
先磨损、后产出，且"挖到了但放不进包"按**没挖到**处理（不回音、不消耗储量之外的东西）——
否则玩家会在背不动的时候白掉耐久。挖矿的节奏是十刻一锄，`MiningSystem`
priority 9，夹在喝药（8）与冷却递减**之间**、且在移动（10）**之前**：
出一锄的那一 tick 要把移动意图清零，人站不住就挥不下去。
按 `F` 却脚下没矿点必须**回音**（"脚下没有矿点"），不然玩家只会以为键坏了
（详见 `docs/数据口径.md` 的《挖矿（P3-S4）》一节）。

**15. 升级的成功率就是纯度，失败罚的是进度不是本金。** 升 +1 级加
**下限 +1 上限 +2**（区间变宽，与幸运 9 的"收窄"互补）；失败**材料全损 + 降 1 级**，
不是原版的"武器碎掉"——单机丢一把 +7 是毁灭性打击，还会逼出"先备份存档再点升级"
的读档流，罚一级进度足够肉疼又不至于劝退。成功率 = 纯度基准 − 当前等级 × 档差，
地板 5%：**纯度决定成功率**是韩版传奇的特色，让挖矿（P3-S4）与锻造（P3-S5）
咬合成一条产业链——挖到的黑铁不再只能卖钱。金币是**服务费，成败都收**
（买的是"这一次尝试"，不是"这一次成功"），且门禁钉住"服务费必须远低于买新"。
随机流 `upgrade:{item_id}:{attempt}`，`attempt` **只增不减**：清零 = 流名重用 =
读档重来掷出同一个数（与 drops 的 kill_index 同一条防线）。
升级改完账本**必须立刻 recompute**——`recompute` 是唯一的属性出口，
不重算的话 "+3" 要等下一次战斗磨损触发重算才生效，玩家看到的就是
"点完了但攻击力没动"。

**16. 祝福油是幸运的第二条腿，诅咒是幸运的镜像。** 掉落之外，幸运的另一个
来源是祝福油：抹一瓶 = 武器 luck +1（上限 9），失败降 1（下限 **−7**）。
`clamp_luck` 因此从 `[0, 9]` 放开到 `[-7, 9]`，`lucky_range` 对负值**对称地压上限**：
`luck = -3` 时 `(22, 36)` 变 `(22, 31)`——诅咒不是"没有幸运"，是**反向的幸运**。
祝福油 `kind = "blessing"`，**不是 consumable**：`is_potion` 的口径是
"带一条合法的 `consume.effect`"，只看 kind 的话"药水负重 / 补货余量 / 自动喝药"
三条都会把它算进去。五只 BOSS 的掉落表**末组**追加祝福油（60‰），
商店同步上架（3000 金）——两条腿缺一条，幸运就只剩氪金一条路。
随机流 `bless:{item_id}:{attempt}` 与升级同一条"只增不减"纪律
（详见 `docs/数据口径.md` 的《武器升级与祝福油（P3-S5）》一节）。

**17. 存档只存真相，派生一律重算；读档顺序是"先派生、后真相、最后钳血"。**
进档的只有**事实**（等级/经验/背包/仓库/穿戴/钱包/技能/图鉴/特戒次数/拍卖账本/
磨损/升级/祝福/死亡账本/坐标/地图/seed/tick/entity_serial/刷怪计时/矿脉账本），
**派生**（六维 dc/mc/sc/ac/mac、luck、max_hp/max_mp、负重）由 `apply_growth` +
`recompute` 读档现算——存了就会跟装备表分叉（改一条装备数据，所有旧档属性全错）。
**运行时**（护盾/中毒/隐身/倒地/麻痹/冷却/挖矿进行时）读档清空：读档 = 重新进图。
读档顺序钉死为「写真相 → 裸身基准 → 叠装备 → **最后**把存档里的当前血钳进新上限」：
顺序反了，"穿 +血装存档、读档时装备已磨穿"会留下一个 200/136 的怪物。
账本纪律全量延续：`Upgrade.attempts` / `Blessing.attempts` / `AuctionBook.next_seq`
/ `DeathLedger` / `entity_serial` / 刷怪计时**全部进档且只增不减**——
清零 = 随机流名重用 = 读档重来掷出同一个数。
校验和用 `fnv1a64`（Python `hash()` 带 `PYTHONHASHSEED` 随机盐，跨进程不一致，
会把好档判成坏档），且有一条约束到**字面量**的测试（期望值写死，
单进程内换 `hash()` 也红）。写盘是 tmp + `os.replace` 原子写：写一半被掐，
留下的是完整旧档而不是半个新档。坏档按码拒读（bad_json / not_a_save /
bad_version / bad_checksum / missing_field / bad_type / no_player / unknown_item），
**绝不**静默当空档继续——丢一条报错好过丢一整局。
自动存档盯四个节点（换图 / 升级 / 死亡结算 / 锻造一次），全部用**轮询 + tick
单调闸门**而不是订阅事件：读档会把 tick 拨回去，事件型钩子会在读档过程中被
触发、把刚读进来的整局原地存回一个半读状态；闸门保证"tick 没变大就什么都不做"，
读档绝不可能引发连锁写盘。F5 存 / F9 读都落在 1 号手动槽——
没有删除确认的槽位选择器，价值不如它带来的误覆盖
（详见 `docs/数据口径.md` 的《持久化存档（P3-S6）》一节）。
