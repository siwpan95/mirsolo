# 数据口径 —— 逐表来源、近似标记与已知差异

> 最后更新：2026-10-19 ｜ 口径：**国服 1.76 复古版骨架 + 韩 2 特色子系统**（D3 = C）
>
> 原则：**每个数字都要能追到来源**；凡属近似，必须显式标 `CALIBRATE`，
> 并在 P1 用实测战斗日志回归校准。绝不把"看着像"当成"就是"。

## 通用约定

| 项 | 约定 |
|---|---|
| 属性写法 | `(下限, 上限)`，对应原版"攻击 0-30"这类区间写法 |
| 六维缩写 | `dc` 攻击 / `mc` 魔法 / `sc` 道术 / `ac` 防御 / `mac` 魔御 |
| 万分比 | 概率与权重统一用 `permille`（10000 = 100%），避免浮点漂移 |
| 等级需求 | 以"穿戴/学习所需等级"为准，不是掉落等级 |
| 单位 | 经验为整数点；时间秒；重量/持久沿用原版整数口径 |

## exp（`data/exp.json`）

- **语义**：`levels["N"]` = 从 N 级升到 N+1 级所需的**本级经验**（不是累计）。`"50": 0` 表示封顶。
- **来源**：公开整理的 1.76 经验表（多来源交叉：VMOS 云手机攻略 / 无度站 / 嘟嘟传奇等），逐值手录。
- **已知差异（重要）**：网上流传"1→50 总经验 10.8185 亿"，但**按该表逐级相加实际为
  `1,044,796,900`（约 10.45 亿）**，差 3,705 万。二者不可能同时成立——网页的"总计"
  与其自身逐级数值不自洽。本项目以**逐级数值**为准（因为升级判定逐级进行），
  `tests/test_exp.py::test_exp_total_matches_table` 钉死 1,044,796,900。
- **影响**：若 P1 拿到更权威的表（如客户端 `ExpList.ini` 的公开整理版），
  只需替换 JSON 并同步该断言，代码零改动。

## classes（`data/classes.json`）

- **语义**：成长字段 `*_per_levels = N` 表示**每升 N 级 +1**，步长固定 1。
  例：`dc_min_per_levels = 4` 即"每 4 级攻下限 +1"。
- **近似标记**：`CALIBRATE`。原版逐级成长表未公开，本表为平滑近似：
  - 1 级战士：HP 20 / DC 1-2 / AC 0-2 / 准确 5 / 敏捷 5 / 负重 30
  - 5 级：HP 36 / DC 2-4 / AC 0-3 / 准确 7 / 负重 38
  - 35 级（裸装）：HP 156 / DC 9-19 / AC 6-13
- **为什么用整数除法**：与确定性随机流同源，跨平台逐位一致；同时避免
  "1 级多加 0.4 点攻击"这种在原版里不存在的半值。
- **P1 校准方法**：用官方/开源服务端公开的 `BaseStats*.ini` 结构做对照
  （只看字段语义与量级，不搬运数据文件），再用实测战斗日志拟合。

## skills（`data/skills.json`）

- **P1-S1 范围**：16 技三职业全覆盖——战士 4（攻杀 7 / 刺杀 19 / 半月 22 / 烈火 32）、
  法师 5（火球 7 / 雷电 17 / 火墙 24 / 魔法盾 31 / 冰咆哮 35）、
  道士 7（治愈 7 / 施毒 14 / 火符 18 / 召骷髅 19 / 隐身 21 / 群疗 26 / 召神兽 35）。
  学习等级按公开资料。
- **`power_permille`**：`CALIBRATE`。原版技能伤害系数未公开，
  这里取"相对强度"近似（烈火 1800 最高、火墙 800 最低）。
- **`kind` 与实现分区**：P1-S2 起 11 种 kind **全部有行为**——
  伤害/治疗（physical / physical_aoe / magic / magic_aoe / taoist / heal / group_heal）
  与状态/召唤（poison / buff_shield / buff_invis / summon）。
  `PLANNED_KINDS` 现在必须为空：**表里新增 kind 而引擎没实现，测试立刻红**
  （`test_no_kind_lags_behind_implementation`）。
  kind 全集唯一定义在 `mirsolo/data/loader.py::SKILL_KINDS`，引擎从那里导入。
- **技能书**：每技一本（`book` 字段 ↔ items.json 里 `kind: "book"` + `teaches` 双向校验）。
  学会即消耗一本；已学再学幂等不吃书。价格 = 500 × 学习等级（`CALIBRATE` 近似）。
- **熟练度**：每成功施放 +1，封顶 3（`MAX_PROFICIENCY`）；被拒的施放不涨。
  P2 再把熟练度接进伤害/命中加成。
- **三道门**：学习（职业 + `level_req`）→ 资源（`cost_mp` + `cooldown`，
  miss 也扣费，与原版"空放就是空放"一致）→ 距离（切比雪夫 ≤ `range`）。
  **被拒的意图直接丢弃并发 `skill:rejected`**——若留在队列里重试，
  冷却一过"几秒前按歪的技能"会自动生效（实测踩过）。
- **AoE 语义**：以**目标**为中心、切比雪夫 `aoe_radius` 内逐个独立结算
  （每个受害者自己的随机流，非伤害均摊）。

## drops（`data/drops.json`）

- **语义**：每组独立 roll 组权重（`permille`，非互斥，可同时掉多组）；
  命中后组内按 `permille` 权重挑一条；`gold` 单独 roll 区间。
- **防刷设计**：结果由 `(world_seed, species, kill_index)` 决定，

- **`CALIBRATE`**：所有权重为初始近似，P1 按"每小时期望收益"校准到原版手感
  （原版典型：小怪 ~1/4~1/8 掉一件普通装备，BOSS 必掉 + 追加组）。

## 战斗公式（`mirsolo/combat/formulas.py`）

| 项 | 公式 | 性质 |
|---|---|---|
| 命中率 | `clamp(7500 + (准确 − 敏捷) × 300, 2000, 9700)` 万分比 BP | `CALIBRATE`：线性近似，原版为分段表 |
| 物理伤害 | `max(1, roll(dc) × 倍率 − roll(ac))` | 结构对齐原版（先命中后 roll 攻防） |
| 魔法伤害 | `max(1, roll(mc) × 倍率 − roll(mac))`，**无视 AC** | 结构对齐 |
| 道术伤害 | `max(1, roll(sc) × 倍率 − roll(mac))` | 结构对齐 |
| 治疗 | `roll(sc) × 倍率`，不抵扣 | 结构对齐 |
| 出手间隔 | `1.50 − 0.10 × 攻速档位`（1.40 ~ 0.40s） | `CALIBRATE` |
| 幸运收窄 | roll 区间下限抬到 `hi − (hi−lo)×(9−luck)//9`（详见《幸运 9》） | `CALIBRATE`：两点精确、中间线性 |

**为什么"最小伤害 = 1"**：原版命中即至少 1 点，这是"高防也磨得死"的底层保证；
若改成 0，低攻角色会被高阶怪永久锁死，与单机（无组队救援）不相容。

### 两套"比率"尺度必须分清（曾经踩过）

| 用途 | 尺度 | 记号 | 100% 等于 |
|---|---|---|---|
| **概率**（命中、掉落组） | 万分比 | `*_BP` / `permille` 字段 | `10000` |
| **倍率**（技能加成） | 千分比 | `power_permille` | `1000` |

事故记录：`resolve_physical` 掷点用 `rand_int(1, 10000)`（万分制），
而命中常量曾按千分制写成 `750`（本意 75%），结果实际命中率只有 **7.5%**，
而"断言 chance 数值"的公式单测全绿——因为**掷点与阈值不同尺度**这件事
没有任何断言在管。现已被两类断言钉住：

1. `formulas.HIT_ROLL_DENOMINATOR` 与命中常量同处一节，注释互指；
2. `tests/test_formulas.py::test_hit_rate_matches_declared_chance`
   直接统计 4000 次真实结算的命中频率，期望值写**字面量** `7500/8400/6600`，
   容差 ±150 BP（注入千分制常量或千分制掷点都会立刻变红）。

**P1 校准计划**：录制 500 场同配置战斗，统计实际命中率与伤害分布，
反推 `HIT_BASE_BP` / `HIT_PER_POINT_BP` 与技能倍率；
校准前后各存一份 `docs/calibration/*.json` 作为证据。

## 幸运 9（P2-S3，`mirsolo/combat/formulas.py`）

传奇口径：幸运来自**武器 + 项链**两个槽，合计封顶 `LUCK_CAP = 9`；
凑到 9 就是玩家口中的"幸运 9，刀刀上限"。

**实现不是"按概率打出上限"，而是把 roll 区间的下限往上抬**：

```
narrowed_lo = hi − (hi − lo) × (LUCK_CAP − luck) // LUCK_CAP
```

| 幸运 | `dc = (22, 36)` 的实际 roll 区间 | 说明 |
|---|---|---|
| 0 | `22–36` | 与没穿幸运装**逐位一致**（不许偷偷改基线） |
| 5 | `30–36` | 只抬高下限（`36 − 14×4//9`），上限永远不变 |
| 9 | `36–36` | 单点，即"刀刀上限" |

选"收窄"而非"概率触发"的硬理由：**幸运 0..8 之间每次结算消耗的随机数个数
完全相同**（`Rng` 是逐次 `next_u64` 推进的流），由
`tests/test_luck.py::test_stream_tail_is_independent_of_luck` 用
"同一条流继续抽一个数、尾数必须相等"钉住。
唯一例外是幸运满时区间塌成单点，它与任何天生就是 `(x, x)` 的区间共用
`rand_int` 的免抽快路径——另有一条专门的测试把两者对齐。

**单机化的两处取舍**（都写在这里，不藏在代码注释里）：

1. **三职业都吃幸运**：原版幸运等价于服务物理攻击（"喝了油的武器"）。
   本项目对 `dc` / `mc` / `sc` 三条 roll 一视同仁，否则法师、道士的幸运装和
   祝福油毫无意义。**治疗与护盾不吃幸运**——它们没有"上下限抽取"这件事，
   套上去治愈术会变成每次刷满，是把一个好想法推过了头。
2. **祝福油没有做成道具**：原版的幸运是消耗品一层层喂出来的，那需要
   **物品实例状态**（同一件 weapon_id 的不同实体要有不同的 luck）+ 一套"使用
   道具"的交互（按键/面板/消耗），属于独立的消耗品批次，强行塞进这一批只会
   做出一个"数据里有、游戏里摸不到"的功能。当前把"已注幸运"直接写进
   终局武器的定义里（赤月系 / 牛魔战斧 `luck: 7`），配合幸运项链 `luck: 2`
   正好凑满 9——效果等价，且三个职业都真的够得着（`verify.py` 的
   `luck-sources` 门禁**按职业分别**验可达，防止"道士一辈子到不了 9"的偏科）。

**链路上有两个可能被漏接的点，各自有测试盯着**：

- `items/equipment.py::recompute` 汇总所有槽的 `luck` 并钳到上限
  （只统计武器/项链这件事由 `luck-sources` 门禁保证，代码里不重复判断）；
- `combat/resolver.py` 把 `Attributes.luck` 递给三条 resolve
  —— 公式改了而这里忘了传，公式单测会全绿，游戏里毫无变化。

## 换图与面板（`mirsolo/world/`、`mirsolo/presentation/panels.py`）

### 传送（踩上去就过）

- 判定是**同格**（切比雪夫距离 0），不是"附近"——站旁边一格就被传走，
  玩家只会觉得地图在抽风。
- 落点 = 目标图里 `to == 来源图` 的那个回程口**向地图内侧偏 3 格**。
  直接落在回程口上会被立刻判定成"又踩到了"，刚进图就被弹回；到达后另有
  2 刻免疫窗口（`portal_grace_until`）兜住极端地图数据。
- 换图**不重建玩家**（`spawn_player` 的 eid 固定，重建 = 清空血量背包等级），
  只搬位置；旧图实体全清，新图按刷新表重铺（与开局同一条路径
  `world.spawn.spawn_map_monsters`，随机流名固定，同图每次进出配置一致）。
- 换图做成 **`PortalSystem`（priority 95，最后跑）** 而不是"窗口每帧查一次"：
  窗口走 `engine.advance()`，headless 走 `session.step()`，两条入口；
  规则写进系统才不会分叉。

### eid 唯一性（静默覆盖，真实踩过）

`World.create_entity` 撞到已存在的 eid **既不报错也不加实体**（实测），
而 `entity_count()+1` 会因清尸体/换图**倒退**——新怪直接顶替活着的旧怪，
表现成"怪凭空少一只"。现在 eid 走 `factory.next_entity_id`：
world data 里只增不减的序号 + 存在性兜底，由
`test_travel.py::test_entity_ids_stay_unique_across_round_trips` 钉住。

### 面板（C 角色 / M 佣兵 / J 图鉴 / N 拍卖行 / B 商店 / V 仓库）

- 布局是**纯几何**（`panels.py`），命中测试、行重叠、出屏都可单测；
  窗口层只负责"把行转成一次规则调用"，**不在窗口里重算价格或门槛**——
  两套判定必然分叉，分叉出来的 bug 只有玩家能碰到。
- 点一次 = 操作**一件**（买卖/存取都是 1，不是整叠）：误点一下卖掉
  20 件药是灾难。
- 商店是**随身商铺**（任意地图可开）——刻意简化：原版商店在城镇里，
  但单机没有"回城"动线，随身商铺的代价可接受；价格仍走 `shop.buy_price`
  单一口径，回收价 = 买入价 // 3，"买进卖出必亏"有用例锁死。
- 货架按 (价, id) 升序；一屏放不下时滚动（滚轮），上下端标"还有几种"——
  直接截断会让技能书永远买不到。
- 钱不够/等级不够的行**保留并显灰**（附原因），不整行消失：
  玩家需要看到自己差多少，而不是猜货架空了一块。
- 六个面板共用一套几何（两栏 + 滚动），`build_panel` 统一派发并**顺带把
  `world` 传下去**（只有佣兵面板要用它读场上队伍）。宁可多传一个参数，
  也不要在派发里按面板名分支——那种分支迟早漏掉新加的面板。
- 图鉴页整页只读（`enabled=False`）：点它只会发出"不能操作"的提示，
  而那句提示本身也是信息。

## sieges（`data/sieges.json`，P2-S1）

- **单机转化口径**：原版是行会互砍争城，单机没有对手，改成
  「攻城小队 vs 守军分层布防」——三道据点（外城门 1200 → 内城门 1800 →
  旗台 2600）依次推进，旗台倒 = 胜，玩家倒/超时（18000 刻 = 30 分钟）= 负。
- **准入锁定**：只有当前波次的目标可被打，其余目标 `invulnerable`——
  「没打下城门就去砍旗台」是打了不结算，不是"砍得动"。
  标记只由 `SiegeSystem` 每 tick 刷（规则层 vs 表现层双入口收敛到一个系统）。
- **守军是普通怪**（`kind="monster"`）：AI/掉落/死亡奖励全复用现有系统；
  **目标是 `kind="guard"`**：无 AI 组件，`DeathRewardSystem` 跳过它
  （奖励由战役结算统一发，避免重复），尸体由 `_retire_wave` 清场——
  `guard` 不被死亡奖励系统移除，不 retire 的话旧城门会一直躺在地上
  （真实踩过：推进波次后场上有 14 个守军 + 两座城门）。
- **确定性**：守军坐标流名 `siege:{map}:{wave}:{serial}`，同种子同阵型；
  增援流名含战役 id 与序号，`max` 封顶（外城 600 刻 1 只、至多 4 只）。
- **奖励**：20000 金 + 中行盔甲/战马刀 + 12000 经验（走 `add_exp` +
  `apply_growth` + 装备重算，与打怪同一条升级路径）；称号「沙巴克城主」
  仅作展示文本，暂无加成——刻意不发明数值。
- **门禁**：`data-integrity` 校验战役图/base_map/守军怪/奖励物品/终局波次
  （必须有 `objective == "banner"` 的波次）全部可解析。

## 特戒六枚（P2-S4，`mirsolo/items/rings.py`）

传奇口径：麻痹 / 护身 / 复活 / 传送 / 隐身 / 火焰六枚戒指，一个角色**同时只能戴一枚**
——`Loadout` 只有单个 `ring` 槽，想换一枚必须先摘下当前这枚。

### 效果写在数据里，代码只认 ID

每枚戒指带 `ring_effect` + `ring_param`；六个效果名与各自的参数键集中登记在
`data/loader.py` 的 `RING_EFFECTS` / `RING_PARAM_KEYS`，由 `validate()` 强制：
ring 槽必带效果、参数不得缺项、非 ring 槽不许带 `ring_effect`。
**没有"戴着玩的普通戒指"这一档**——留这个口子，后面就会出现"表里有一枚戒指、
代码不认识它"的死数据。

| 戒指 | 触发时机 | 单机口径 | 参数 | 数据表实测值 |
|---|---|---|---|---|
| 麻痹 | 攻击命中 | 掷万分比，中了给目标挂 `Paralysis` | `bp` / `ticks` | 300bp / 20 刻 |
| 护身 | 自己挨伤害 | 按比例把 HP 损失换成 MP，蓝不够的照扣血 | `permille` | 1000‰ |
| 复活 | 自己即将致死 | 在 `take()` 之前拦下，回 `hp_permille` 并扣一次额度 | `charges` / `hp_permille` | 3 次 / 500‰ |
| 传送 | 主动（`T` 键） | 固定回城点 + 冷却，走 `world.travel.travel` | `map` / `cooldown_ticks` | biqi_field / 300 刻 |
| 隐身 | 持续 | 每刻刷新 `Invisible`；出手破隐，过 `recover_ticks` 再结 | `ticks` / `recover_ticks` | 40 / 30 刻 |
| 火焰 | 攻击命中 | 追加一次**不看目标防御**的伤害 | `power_permille` | 300‰ |

### 两套比率尺度在这里继续生效

概率一律万分比 `*_bp`（掷点 `rand_int(1, 10000)`），倍率一律千分比 `*_permille`
（1000 = 100%）。《两套"比率"尺度必须分清》那节写过的 10 倍坑，特戒上同样成立：
`protect` 的参数是 `permille`（1000‰ = 全额代偿），不是 `bp`；
`paralysis` 才是 `bp`。两者写反的后果是"要么 100% 触发，要么 0.03% 都不触发"。

### 改血顺序是硬纪律

```
Shield.absorb → rings.split_protect → rings.try_revive → Vitals.take()
```

- **吸收层在外、致死判定在内**：反了的话，戴着护身还套着魔法盾的玩家会把两层
  吸收叠成同一个血池——两层变相加，耐久直接翻倍；
- **复活判定必须排在 `take()` 之前**：一旦先扣成 0 血再救回来，`EVT_DEATH`、
  尸体清算、攻城判负这些副作用已经发出去了，救不干净；
- **致死边界是 `amount >= vitals.hp`**：写成 `>` 会漏掉"伤害正好等于剩余血量"
  这一格。这条由 `test_revive_covers_the_exact_lethal_boundary` 钉住——它是注入
  验证的产物（原本的实现被改坏后测试居然还是绿的，于是补了这个用例）。

四段接线全部落在 `CombatResolver._damage`（resolver.py:108 与 :117）这一个入口里，
因为那是全项目**唯一允许改血的地方**。新机制想改血，只能挂在这里。

### 随机流必须独立

麻痹掷点与火焰伤害走**名字里带 `ring:` 前缀**的独立流（`ring:paralysis:…` /
`ring:flame:…`）。理由与幸运 9 完全一致：戴上或摘下戒指，不能挪动主伤害流的位置，
否则同一份存档戴戒指前后打出来的每一刀都对不上，回放无从谈起。
`test_ring_rolls_leave_the_main_stream_untouched` 用"300 刻逐位对齐"把这条钉住。

### 三处单机化取舍（都写在这，不藏在代码注释里）

1. **一个槽、一枚戒指。** 开放双戒指会让护身 + 复活叠加，"这刀到底死没死"变得
   无法讨论，而两两搭配的平衡工作在单机里收益极低。
2. **传送戒指指向数据里写死的回城点**，不是"记录上次落脚点"。后者要一套让玩家确认
   坐标的 UI，成本远高于收益；固定点还能被 `ring-effects` 门禁校验（地图存在、
   冷却为正），不会出现"戒指指向一张不存在的图"。原版随机传送卷的风险与惊喜，
   单机里交给地图设计而不是道具。
3. **`RingState` 与 `Loadout` 解耦。** `recompute` 每次穿脱装备都全量重算属性，
   而"复活还剩几次"是跨次数的账本，不能跟着重算——否则换一身装备就白送复活。
   已知的取舍：`charges` 按 `item_id` 记账，同名戒指来回脱穿共用一份剩余次数
   （当前只有一枚复活戒指，因此这个取舍暂时观察不到；等真的要开放多枚戒指时，
再改成按物品实例记账）。

## 拍卖行（P2-S5，`mirsolo/economy/auction.py`）

### 单机化：寄卖行 + 确定性撮合

原版拍卖行是玩家对玩家的 C2C 市场，靠的是"服务器里还有别人"。单机没有别人，
所以"卖给谁"必须重新定义：这里做成**寄卖行**——玩家把东西挂给 NPC 行会，
系统按固定节奏（每 600 刻 = 60 秒）掷点决定"这一轮有没有人来买"。

**为什么不做"AI 买家还价"**：让 NPC 报一个价、玩家决定卖不卖，需要一套还价 UI
和一轮往返交互，成本远高于收益；而"玩家定价 + 概率成交"把决策压成一次点击，
并且概率与要价的关系是**可验证的线性函数**（挂底价必按 `demand_bp` 成交，
顶到上限永远不成交），单测能直接钉住。

### 四条约束，缺一条就退化成提款机

1. **要价有上限**：`cap` = 商店买入价 × 1200‰（`CAP_PERMILLE`）。没有上限，
   挂 100 万金也照成交，金币就不再是稀缺资源。
2. **越贵越难成交**：概率从 `demand_bp` **线性衰减**到 0。刻意选线性——
   任何"更自然的曲线"都只能靠肉眼调，而调出来的数没人复查。
3. **成交扣 10% 手续费**（`FEE_PERMILLE = 100`）：钱是系统凭空造出来的
   （AI 买家），必须有回收。
4. **挂单即离手**：物品进托管，不能"挂着还能穿、还能卖"——同一件装备
   不允许有两个去处。撤单是唯一的取回路径，且背包满时**整笔拒绝**
   （不部分退回：那等于凭空多一个隐形仓库）。

三档报价（速卖 0‰ / 常价 500‰ / 高价 900‰）刻意**不顶到 1000‰**：
顶到上限成交概率恒为 0，"高价"这一档就成了摆设。

### 数值口径

- `demand_bp` 是**万分比**（`rand_int(1, 10000)`），与麻痹概率同一把尺子；
  `floor_permille` / `CAP_PERMILLE` / `FEE_PERMILLE` 是**千分比**（1000 = 100%）。
  两类比率混用在本项目踩过一次，见《两套"比率"尺度必须分清》。
- 按装备等级分四档需求度：≤15 级 400bp、≤30 级 550bp、≤44 级 700bp、
  45+ 级 850bp；技能书单独一档 600bp。底价 `floor_permille` 分别取
  500/550/600/650‰（技能书 550‰）——都**高于**商店回收价（1/3），
  由 `auction-book` 门禁钉住"寄卖必须比卖商店划算"，否则拍卖行就是白做的。

### 随机流

流名 `auction:{seq}@{round}` —— 含**挂单序号**与第几轮，不含调用顺序。
两条纪律：

- 多挂/少挂一张单，不会挪动别的单的随机数位置；
- 两张单不能**共用**一条流（流名里漏掉 `seq` 会让它们的成交永远同步），
  `test_two_listings_do_not_share_one_random_stream` 用 40 个种子钉住这一点。

挂单序号 `next_seq` 只增不减：它进了流名，撤单回退会让两张不同的单共用同一条流。

## 佣兵与图鉴（P2-S6，`mirsolo/actor/mercenary.py`、`codex.py`）

### 佣兵：花金币买**一段时间**的友军

| id | 名字 | 门槛 | 价格 | 时长 | 同名上限 |
|---|---|---:|---:|---:|---:|
| `gubing` | 雇用兵 | 20 级 | 8000 金 | 300 秒 | 3 |
| `huwei` | 虎卫 | 35 级 | 35000 金 | 300 秒 | 2 |
| `mofashi` | 魔法侍卫 | 50 级 | 150000 金 | 300 秒 | 1 |

三条约束：**要花钱**（不是白送的宠物）、**有等级门槛**（唯一挡住"1 级雇侍卫平推
全图"的东西）、**到点必走**（不给永久随从，否则"佣兵"就变成第二个角色）。

- **不新增实体种类**：佣兵的身体与怪物同构，走 `_build_combatant` 同一条构造
  路径，只靠 `kind="summon"` + `faction=0` 就让索敌/追击/出手/死亡清理全部生效。
  多造一个 "merc" 种类要改四处判定，漏一处就表现成"佣兵不动手"或"尸体留在场上"。
- **两个上限各自生效**：`max`（数据表的同名上限）卡"同一种别带一堆"，
  `SQUAD_LIMIT = 4`（全局）卡"别带一个班"。`merc-hire` 门禁要求
  `sum(max) > SQUAD_LIMIT`——够不着的约束是死代码，而死掉的约束最危险：
  它看起来在保护平衡，其实什么都没做。
- **到期由 `MercenarySystem`（priority 7，出刀之前）直接移除**，不留尸体：
  佣兵没有掉落也没有刷新表，留尸体只能靠死亡清理那条路，而到期根本走不到那里。
- ⚠️ **已知取舍：换图不带走佣兵。** `travel` 会清掉除玩家外的所有实体，
  所以佣兵与召唤物换图即消失。这是既有行为、不是佣兵引入的 bug，
  但面板上必须写清楚（`test_mercenaries_do_not_survive_a_map_change` 把现状钉住），
  否则玩家会以为自己的 15 万金被吞了。

### 图鉴：只记击杀，奖励只给第一次

- **解锁 == `kills` 里这个 key 存在**，不另存一份 `unlocked` 集合。两份事实
  描述同一件事，迟早分叉（杀了却没解锁 / 解锁了却显示 0 杀）。
- **不记"见过"**：见过没杀过的怪玩家拿不到任何信息，列在图鉴里只是一行灰字。
- **首次解锁给经验**（该怪经验的 500‰），**不给属性点**：属性点会让战力脱离
  职业成长表，升级曲线就对不上了；经验是一次性的、可预期的，只让你**早一点**
  升级，不会让你**多一点**属性。第二次击杀不再发奖（`test_second_kill_adds_no_bonus`）。
- **佣兵/召唤物的击杀记到雇主头上**：`CodexSystem` 订阅 `EVT_DEATH`，并复用与
  死亡奖励**同一个** `resolve_owner`。各写一份归属解析的话，加了"第二层归属"
  就只有一处会跟着改，另一处静默算错人。
- ⚠️ 图鉴在 `DeathRewardSystem`（priority 40）**之后**跑（41），而尸体在 40 就被
  移除了——所以 `species` 与归属必须**在事件回调里**取好，不能等 `update`
  （回调发生在 `emit` 那一刻，尸体还在场）。
- 面板按 (等级, id) 升序、两栏共用同一个 scroll：左边第 3 行和右边第 3 行必须
  说的是同一只怪；右栏写**物品名**不写概率（玩家在图鉴里查的是"出什么"）。

## 装备持久度与修理（P3-S1，`mirsolo/items/wear.py`）

### 数据表里的 durability 躺了两批

22 件装备（`slot` 非空的那些）**全部**自带 `durability`，取值 8..30；另外 16 件
非装备（`kind` 不是 `equip`）写 0。也就是说"装备会坏"这件事在数据上早就成立，
但 P1、P2 没有任何系统读这个字段——它是一份没人执行的承诺。P3-S1 做的就是把它
接进战斗回路，并补上"坏了怎么办"。

### 三条硬规则

1. **磨损只由"真的命中"产生**：Miss 不记。反过来写会出现"躲得越好、装备坏得越快"，
   玩家一眼就能看出不对。
2. **磨穿 = 属性一分不给，但装备还在、还能脱下来**。让玩家看得见"我为什么变弱了"，
   而不是东西凭空消失。
3. **洗掉磨损只能花钱**：要么修理，要么卖掉再买一件新的（两条路都在入手/修好时
   重置账目）。不花钱就能洗白的路径一律不留。

### 磨穿了还占负重

`recompute` 里先累加 `gear_weight`、**再**判断 `is_broken` 并 `continue`。顺序反了
（先跳过再加重量）,"把装备打废"就成了免费减重——一种**收益**，与"装备坏了是惩罚"
的初衷正好相反。

### 为什么按 item_id 记账

背包是堆叠的（`item_id -> 数量`），没有实物实例 id，所以磨损记在
`Wear.points[item_id]` 上，语义是"这一类装备里**最破的那件**"。

这个语义刚好堵住一个空子：打废一把木剑、换上背包里另一把木剑，磨损照旧继承——
想洗掉只有花钱。若按"第几件实物"记，换一把就洗白，修理系统直接失去意义。

同样的理由，`Wear` 必须和 `Loadout` **解耦**（与 `RingState` 完全一致）：
`Loadout.slots` 是"当前穿着"的真相，每次穿脱都会被 `recompute` 全量重算；
磨损是**跨次数的累计账本**，跟着重算就等于每穿脱一次免费修一次。

### 数值口径

- `WEAR_BP_PER_HIT = 300` 是**万分比**（3%，与麻痹戒指同一把尺子）。
  期望寿命 = `durability × 10000 / 300`，即 **267~1000 次命中**
  （8 点耐久 267 次，30 点耐久 1000 次）——够打一两张图，又不至于整局不用管。
- `REPAIR_PERMILLE = 300` 是**千分比**：修满一件 = `买入价 × 300‰ × 已磨损比例`，
  向上取整、**至少 1 金**（磨了一点也要收钱，否则"每次磨 1 点就修一次"能白嫖）。
- 门禁 `wear-and-repair` 三查：`durability` 必须为正、全废修理费必须 **`<` 买入价**
  （贵过买新的话修理按钮就是摆设）、期望寿命落在 **100~5000 次命中**区间。
  三条都能在 `verify.py --selfcheck` 里靠注入变红。

### 两条独立随机流

- 出手方：`wear:strike:{eid}@{tick}` —— 磨**武器**；
- 挨打方：`wear:hit:{eid}@{tick}` —— 磨**防具**（`weapon` 槽排除在外，
  挥刀砍钝的是刀，挨揍砸烂的是甲，两条账各算各的）。

流名只含自身实体 id 与 tick，戴上/摘下装备都不得挪动别的流。
`test_wear_streams_do_not_shift_the_damage_stream` 把 `WEAR_BP_PER_HIT` 改成 0
重打同一场架，断言伤害序列**一字不差**。

### 单机化取舍

- **磨穿不销毁装备**：原版武器持久见底会消失/破碎；单机丢装备惩罚过重，
  而且和"读档重打"天然打架。
- **按 id 不按实物**：见上，是为了堵空子，也为绕开"堆叠背包没有实例 id"。
- **怪物没有 `Wear` 账本**：`defender.get(Wear)` 为 `None` 就直接返回，
  既不磨怪物、也省一条流。给怪物记磨损没有玩法收益——它不掉装备。

### 已知差异（原版对照）

原版是每件实物独立耐久、且见底会破碎消失；本作按 id 记账且不销毁。
差异是刻意的，写在模块 docstring 里，不视为缺陷。

## 死亡惩罚（P3-S2，`mirsolo/actor/penalty.py`）

### 时序：先倒地，再选怎么起来

::

    致死那一下 → 发 EVT_DEATH → 玩家进入 Downed（HP=0，**还没结算**）
                                  ├─ 30 刻内按 R  → 原地复活（花金币，只掉磨损）
                                  └─ 满 30 刻     → 自动回城（免费，四件惩罚全额）

**为什么惩罚要推迟到玩家做出选择时才结算**：原地付费复活卖的就是"少掉点东西"。
若死亡瞬间先扣光、原地复活再退回来，就得写一套退款逻辑——退多少、掉出去的物品
怎么吐回来、吐回来的还算不算"掉过"，全是说不清的账。推迟结算之后两档各算各的，
**没有退款这条路径**。

**为什么还要留一个自动回城兜底**：headless（`cli/smoke.py`、存档回归）没有交互，
倒地之后必须有确定行为；玩家死了不操作也不会把游戏卡住。
`DOWN_TICKS = 30`（3 秒）由门禁 `death-penalty` 钉住必须为正。

### 四件惩罚（全额 = 回城）

| # | 惩罚 | 口径 | 常量 |
|---|---|---|---|
| 1 | 掉经验 | 本级升级所需经验 × 100‰，**只掉本级已积累的部分** | `EXP_LOSS_PERMILLE = 100` |
| 2 | 掉金币 | 持有金币 × 100‰ | `GOLD_LOSS_PERMILLE = 100` |
| 3 | 全身装备额外磨损 | 身上每件 **+1 点（必然，不是概率）** | `DEATH_WEAR_POINTS = 1` |
| 4 | 随机掉一件背包物品 | 20% 概率掉 **1 个**（堆叠只掉 1 个） | `BAG_DROP_BP = 2000` |

**原地付费复活**：`500 + 100 × 等级` 金，惩罚只剩第 3 件（磨损）——
花钱买的就是"不掉经验金币、不掉东西、位置不动"。钱不够就拒绝并提示还差多少，
**不做赊账**：金币一旦允许为负，商店回收价与拍卖行底价全都得跟着处理负数。

### 绝不掉级

`capped_exp_loss = min(应扣, prog.exp)`——只从**本级已积累**的那部分扣，
扣到 0 就为止，等级数字永不回退。这也意味着"刚升完级就死"几乎不掉经验：
惩罚自然与"这一级打了多久"成正比，不需要额外规则。

满级（经验表封顶 52 级，`exp_to_next == 0`）返回 0：没有下一级可掉，
在这一项上再扣就是在惩罚里挖一个看不见的洞。

### 随机流

`death:{eid}@{tick}` —— 只用于挑"掉背包里哪一件"。
带自身实体 id 与 tick，不挪动主伤害流，也不挪动磨损流。

### 单机化取舍

- **只掉背包里不穿的东西**，身上的装备一件不动。原版 1.76 死亡有几率掉
  **身上穿着**的装备（红名尤甚）；单机丢掉辛苦打来的装备惩罚过重，
  而且"掉了就读档重打"会养成存档投机，与 P3-S6 的防刷口径直接打架。
- **累计流水挂在 `DeathLedger` 独立组件上**，不挂在 `Progression` 上——
  读档时 `Progression` 会被存档整个覆盖，跟着覆盖就等于"死了读档撤销惩罚"。
  账本只增不减，存档读写层沿用。
- **金币绝不为负**（夹取），不引入负债。

### 已知差异（原版对照）

原版是"掉经验 + 有几率掉身上/背包物品"，红名惩罚更重；本作固定四件、
比例固定、只掉背包。差异是刻意的：单机要的是**可预期的代价**，
而不是"这一次运气不好，一身装备没了"。
